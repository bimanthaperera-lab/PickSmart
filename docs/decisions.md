## 2026-10-22 — Phase 0 scaffold

- **Toolchain versions.** AGP 9.4.1, Kotlin 2.4.21 (AGP's built-in Kotlin plus the Compose compiler plugin), Gradle 9.8.2, Compose BOM 2026.09.00, compileSdk and targetSdk 37, minSdk 26. These match the owner's other Android project, which already builds on this machine with these versions cached. *Default.*
- **JDK.** Gradle runs on Android Studio's bundled JBR (JDK 25), since no separate JDK 17 is installed. Bytecode targets Java 17 (`sourceCompatibility` and `targetCompatibility` 17), which is how the "JDK 17" rule in CLAUDE.md is met. Set `JAVA_HOME` to `C:\Program Files\Android\Android Studio\jbr` before running Gradle from a terminal. *Default.*
- **Package.** `lk.picksmart` for both the namespace and the application ID, until the owner decides. *Default.*
- **Repository.** GitHub `bimanthaperera-lab/PickSmart`, branch `main`. *Owner.*
- **Auto Backup.** On, with explicit rules (`backup_rules.xml` and `data_extraction_rules.xml`) that include only the Room database and the `datastore/` files. Caches are never included. *Default (PLAN.md open question).*
- **Launcher icon.** A plain yellow pin on a near-black background is a placeholder until the owner's logo source is added to `design/brand/`. The real adaptive icon follows the rules in CLAUDE.md section 9. *Default. Superseded on 2026-10-22, below.*
- **Secrets.** `google-services.json` is in `.gitignore` along with keystores and `local.properties`. *Default.*
- **Known issue for Phase 2.** Brand yellow text on the light background has low contrast. The light theme needs a darker accent for text, with yellow reserved for fills. *Default.*

## 2026-10-22 — Brand logo in the app

- **Logo source.** The owner's `picksmart-logo.jpeg` lives in `design/brand/`. It's a raster image on a dark gradient, so the mark and wordmark are traced into vector drawables (`design/brand/trace_logo.py` and `make_drawables.py`, explained in `design/brand/README.md`). If the owner later supplies an SVG, regenerate from that instead. *Owner asked; tracing method is the default.*
- **Launcher icon.** The adaptive icon uses the traced pin mark, 58 of 108 units tall, centred inside the 66 dp safe zone, on a near-black background. The monochrome (themed) icon uses the same paths in one colour; the dark gaps in the mark keep the white P readable. *Default.*
- **Brand colours in the logo.** The traced logo uses the flat brand colours (yellow `#FBBB23`, off-white `#F5F5F2`) instead of the slight gradient in the JPEG. *Default.*
- **Start screen.** It always uses the dark theme and light system bar icons, because the full logo is only legible on a dark surface. The window background is near-black in both modes, so there's no light flash at launch. Phase 2 revisits this when the app shell arrives. *Default.*

## 2026-10-22 — Phase 1 ProfitCalculator

- **Commission as one whole number.** `ProfitInput.commissionHundredths` holds the commission in hundredths of its unit: cents for `AMOUNT` (Rs. 200 = 20000) and hundredths of a percent for `PERCENT` (20% = 2000, 12.5% = 1250). Both types stay an exact `Long` with no `Double`, and percentages are precise to 0.01%. The `Trip` entity will store the same value. *Default.*
- **Net profit from rounded parts.** Fuel, reserve, commission and per-km values are each rounded HALF_UP to cents. Net profit is computed from those rounded parts, so the breakdown on screen always adds up to the net shown. *Default.*
- **Band uses the rounded per-km value.** The target comparison uses the same rounded profit per km the rider sees, and meeting the target exactly counts as `GOOD`. A loss is always `LOSS`, even with a target set. With a target but zero distance, the band falls back to `PROFIT` or `BREAK_EVEN`. *Default.*
- **Validation.** Every problem is returned at once as typed `ValidationError`s, each tied to an `InputField`, so the UI can mark each field. NaN or infinite numbers are rejected. Commission isn't validated in payout mode, because that field is hidden. Results too large for a `Long` return `ResultTooLarge` instead of overflowing or throwing. *Default.*
- **Gradle daemon JVM.** Android Studio generated `gradle/gradle-daemon-jvm.properties`, which pins the daemon to JDK 25. It's committed, consistent with the JDK entry above. *Default.*

## 2026-10-22 — Phase 2 design system and app shell

- **Colours.** The dark theme follows the mockups: near-black `#0D1112` background, `#1A1F1F` cards, green profit, red loss, amber below-target. In the light theme, yellow fails contrast as text on white, so Material `primary` (text, focus, selection) is a dark amber `#7A5000` and `primaryContainer` stays brand yellow for filled primary buttons. Profit, loss and below-target colours live in `PicksmartTheme.status`, because Material has no roles for them. *Default.*
- **Icons.** No icon library. The 11 outline icons are hand-drawn 24-unit vector drawables, matching the mockups' line style, so there's no extra dependency. *Default.*
- **Money format.** `MoneyFormatter` puts a non-breaking space between "Rs." and the number so they never wrap apart, always uses Western digits and comma grouping (`Locale.US` symbols), and takes the prefix from `strings.xml` (`currency_prefix`) so it can be translated. Negative amounts are `-Rs. 50.00`, and signed profit is `+Rs. 705.00`. *Default.*
- **Number input.** `sanitizeDecimalInput` keeps only digits and one decimal point. A dot counts as the decimal point only after a digit (or at the very start) and before a digit (or at the end), so pasting "Rs. 1,000.00" gives `1000.00`, not `0.10`. *Default.*
- **Theme preference brought forward.** The Settings theme choice (System / Light / Dark) is saved now in DataStore (`user_preferences`, key `theme_mode`) through `UserPreferencesRepository`, so Settings has a real control rather than a placeholder. Unknown stored values fall back to System. *Default.*
- **No theme flash.** `MainActivity` waits for the stored theme before drawing, and the window background (off-white in light mode, near-black in night mode) shows for that moment. *Default.*
- **Navigation.** Navigation Compose with `@Serializable` routes. Switching tabs pops back to Home and restores each tab's state, so Back from any tab returns to Home and Back from Home leaves the app (checked on the emulator). *Default.*
- **Bottom-bar labels at large font sizes.** Five tabs on a 360 dp phone leave about 72 dp each. At 200% font, "Check Ride" can't fit, so the tab labels shrink to fit one line (8 dp minimum) instead of being cut off. Screen readers always get the full text. All other text scales normally. *Default.*
- **Tab content before data exists.** Home, Check Ride, History and Reports show honest empty states until their phases land (4, 5 and 7). Check Ride says it's coming soon; it gets its form in Phase 4. *Default.*
- **Lint warnings accepted.** `VectorPath`/`VectorRaster` on the traced logo (an accurate trace needs long paths, and it's drawn once and cached), `ObsoleteSdkInt` on `mipmap-anydpi-v26` (AAPT fails to find the adaptive icon without the `-v26` suffix), `UnusedResources` on `picksmart_logo` (onboarding uses it in Phase 3), and `GradleDependency` for DataStore 1.3.0 (staying on the cached 1.2.1). Lint reports 0 errors. *Default.*

## 2026-10-22 — Phase 3 persistence and onboarding

- **Vehicle table v1 has every Vehicle field from CLAUDE.md section 8**, including `fuel_type`, `fuel_price_source`, `fuel_price_effective_date` and `auto_update_fuel_price`. PLAN.md had planned to add those in Phase 6b with a migration; putting them in v1 (before any release) avoids that migration. Columns are snake_case, enums are stored by name, dates as ISO `yyyy-MM-dd` text, and timestamps as UTC epoch millis. *Default.*
- **`is_sample` column.** A vehicle created with "Skip and use sample values" is flagged in its own row, so the "Sample" label follows the vehicle (and survives backup and restore) until the rider saves the form. Any save from Edit vehicle clears it. *Default.*
- **Sample values** are the CLAUDE.md G1 test numbers: Motorcycle, Petrol 92, Rs. 300.00/L, 40 km/L, Rs. 2.00/km reserve, no target. They are not real prices and are always labelled "Sample". *Default.*
- **Onboarding** is a welcome screen, then two steps (vehicle, then the safety notice). Nothing is saved until the rider accepts the notice; then the vehicle is inserted and `default_vehicle_id` and `onboarding_complete` are written in one DataStore edit. If the app dies first, setup simply runs again. The flag is never cleared by code. Fuel type is asked during setup (needed later to match published prices). A blank vehicle name defaults to the vehicle type ("Three-wheeler"). The mockup's "I already have an account" link waits for Phase 8c. *Default.*
- **Fuel price rules on edit** (CLAUDE.md section 8a): changing the fuel price or the fuel type by hand sets the source to `MANUAL`, clears the effective date and turns auto-update off. Editing other fields keeps a published price as it is. *Default.*
- **Edit vehicle** is one route, `EditVehicleRoute(vehicleId)`, where `0` means "add". The first vehicle created becomes the default. The mockup's separate "Fuel price & type" screen (Phase 6b), the "Default vehicle" switch and the archive action (multiple vehicles, Phase 8d) are left out for now; fuel type and price are edited inline. *Default.*
- **Last-used Check a Ride inputs** move to Phase 4, where the form decides exactly what is remembered. *Default.*
- **Schema safety net.** `SchemaTest` (device test) creates a database from the committed `1.json`, writes a row with raw SQL, and opens it with the app's real builder and `ALL_MIGRATIONS`. An entity change without a version bump and migration fails that test. The Room Gradle plugin supplies the schema files to device tests. *Default.*
- **Large fonts.** `ChoiceGrid` measures its labels and drops from two columns to one when a label can't fit a tile on one line, instead of breaking words. *Default.*
- **Welcome screen bars.** The welcome screen is always dark (the full logo needs it), so it forces light status and navigation bar icons and restores the theme's setting when it leaves. *Default.*

## 2026-10-22 — Phase 4 Check a Ride

- **What is remembered.** Fare mode, commission type and value, other costs, and the three distances are saved in DataStore (`check_*` keys) 0.4 s after the rider stops typing. The fare is never remembered, because a stale fare would show a result that looks like an answer for the new offer. Per-check rate overrides are not remembered either, so a new session always starts from the vehicle's rates. An empty field is stored as an absent key. *Default.*
- **Common case is three edits.** With the fee remembered, a new offer needs the fare, pickup and trip. The fare starts empty and focused, and has a clear button. *Default.*
- **Default commission type** before the first check is a percentage with an empty value (counted as 0). No rate is suggested (CLAUDE.md section 2). The "Rs." / "%" switch sits inside the fee field, as in the mockup. *Default.*
- **Result pinned above the keyboard.** On a 360 × 640 dp phone the form alone fills the screen, so the result is pinned to the bottom, above the keyboard (`imePadding`), and the form scrolls above it. While the keyboard is open only the band, net profit and per-km show; the breakdown appears when it closes. The panel never takes more than 55% of the height and scrolls inside beyond that. *Default.*
- **One source of validation rules.** The form only checks that text parses and that overridden fuel price and efficiency aren't empty. Range rules (percent above 100, efficiency of 0, results too large) come from `ProfitCalculator`'s own validation and are mapped back onto fields. The calculation still runs with an empty fare (as 0), so a 150% fee is flagged before the fare is typed. *Default.*
- **Per-check overrides** cover fuel price, efficiency and maintenance reserve. The target stays the vehicle's. "Change" starts them from the vehicle's current rates, and "Use vehicle rates" drops them. They never change the saved vehicle. The "Sample" label shows only while the vehicle's own sample rates are in use. *Default.*
- **Band lines.** "Good · meets your Rs. 60.00/km target" (the mockup says "above"; `GOOD` includes meeting the target exactly), "Below target · under your … target", "Loss · this ride costs more than it pays", "Break-even · no profit, no loss", and plain "Profit" with no target. *Default.*
- **Left for later phases.** The mockup's platform chips and the "Save offer" / "I took it" buttons need the `Trip` table (Phase 5). The scan icon is Phase 8 (OCR). Neither is shown now, so there are no placeholder controls. *Default.*
- **Large fonts.** Above 130% font, side-by-side fields stack full width, and the breakdown uses two columns instead of three. The fare-mode segments share one height when a label wraps. *Default.*
- **Missing default vehicle.** Check a Ride offers "Add your vehicle". A vehicle added from there (or Settings) becomes the default whenever the current default is missing, not only when no id is stored. *Default.*

## 2026-10-22 — Phase 5 trips, history and other income

- **Database v2** adds `trips` and `other_income`; `vehicles` is unchanged. `MIGRATION_1_2` uses the exact SQL from the exported `2.json`, and `MigrationTest` validates it. The update from the Phase 4 build was also tried by hand on the emulator. *Default.*
- **Extra trip columns beyond CLAUDE.md section 8:** `updated_at` (needed by the last-write-wins sync in section 14, so no later migration) and `target_profit_per_km_cents_snapshot` (so a past trip's band never follows a later target change). Trip time is stored as UTC epoch millis; the day it belongs to is its Asia/Colombo date. *Default.*
- **No foreign key from trips to vehicles.** Vehicles are archived, never deleted, and a cloud restore (Phase 8c) may write trips before their vehicle. `vehicle_id` is indexed. *Default.*
- **Deletes are hard deletes for now**, always after a confirmation dialog. Sync tombstones arrive with Phase 8c, when there is a cloud copy to keep in step. *Default.*
- **"Save offer" and "I took it".** "Save offer" saves an `OFFER_CHECK`. "I took it" saves a `COMPLETED` trip at once, timed now, with the checked values, because the rider has seconds and is stopped. The trip can be corrected later from History. On a loss the button reads "Took it anyway" and isn't yellow. After either save the fare and any rate overrides clear for the next check, and a snackbar offers "View" (History). The saved snapshot is the rates the check actually used, overrides included. *Default.*
- **Platform** is chosen with chips on Check a Ride and remembered with the other inputs (new DataStore key `check_platform`, added without touching existing keys). It starts as Uber. *Default.*
- **Cancelled trips** count the fee (0 when none) minus estimated fuel and reserve for the pickup plus return. They carry no commission and no other costs, and saving a cancelled trip clears its trip distance and other costs. The offered fare is kept but never counted. A non-cancelled trip never keeps a cancellation fee. *Default.*
- **Marking an offer.** Opening an offer in History shows Offer / Completed / Cancelled. A completed or cancelled trip can't go back to being an offer. The rider confirms the values by saving. *Default.*
- **Editing a trip** keeps its own rate snapshot, shown as "Calculated with …"; it never picks up the vehicle's newer rates. A new trip from "Add trip" snapshots the default vehicle's current rates and takes the platform and fee setup from the last check, with distances empty. Dates after today can't be picked. *Default.*
- **History day totals** read "Est. profit Rs. …". They are the estimated profit of that day's shown completed and cancelled trips. A day with only offers shows no total. Offers are listed with a dashed outline, an "Offer" tag, "Not counted as income" and "… est.". The totals use the same `countedProfitCents` that Phase 7's accounting use case will build on. *Default.*
- **Other income** is reached from Home and Settings → Records. Its help text tells riders that cancellation fees belong on the cancelled trip, not here, so they are never counted twice (the mockup suggested entering them as income). The amount must be above 0, and the platform is optional ("None"). *Default.*
- **Large fonts.** Above 130% font, a History row puts its amount under the details instead of in a side column, and the trip status uses scrolling chips instead of segments, so no word or number breaks mid-way. *Default.*

## 2026-10-22 — Phase 6 fuel log and expenses

- **Database v3** adds `fuel_logs` and `expenses`; existing tables are unchanged. `MIGRATION_2_3` uses the exact SQL from the exported `3.json`, and `MigrationTest` checks that a v2 vehicle, trip and income row survive. Both tables carry `created_at` and `updated_at` for the sync in section 14. Like trips, there is no foreign key to vehicles (`vehicle_id` is indexed on fuel logs). *Default.*
- **Fill-up form.** The rider types either the amount paid or the litres, and the other is worked out from the price per litre (litres to 2 decimals, money half up to the cent), marked "Worked out from the price". The price starts from the vehicle's price and can be changed for that fill-up only; it never changes the vehicle. The amount paid is what is stored as `totalCents` and what cash profit will use. Full tank starts off. A new fill-up needs a vehicle ("Add your vehicle" otherwise). *Default.*
- **Actual km/L** (`latestEfficiency`): the latest pair of full-tank fills that both have an odometer reading; km between them ÷ every litre added after the first, including partial fills and full fills without a reading in between. Fills are ordered by date, then entry order. A pair whose odometer didn't go up is skipped for the one before it. Shown to 1 decimal, with "This assumes every fill-up in between is recorded". *Default.*
- **Efficiency suggestion.** Offered when the reading differs from the vehicle's setting by 10% or more. "Use … km/L" changes only the vehicle's efficiency (the sample label and fuel price settings stay as they were); past trips keep their snapshot. "Not now" is remembered per reading in a new DataStore key, `dismissed_efficiency_log_id`; the next full-tank reading can be offered again. The setting is never changed automatically. *Default.*
- **Expenses** have no fuel category, and both list screens say fuel belongs in the Fuel log. A new expense belongs to the default vehicle when one exists (null otherwise); editing keeps it. The odometer field shows only for Maintenance & repair, and a reading typed under another category is not stored. Default category is Maintenance & repair. The amount must be above 0. *Default.*
- **Where they live.** Fuel log, Expenses and Other income are reached from Home and Settings → Records through one shared `RecordsGroup`. Each list shows this month's total. Deletes are hard deletes after a confirmation dialog, as for trips. *Default.*
- **Shared record UI.** The income screen's header, row and month card moved into `ui/components` (`DetailHeader`, `RecordRow`, `MonthTotalCard`) so the three record screens look and behave the same. At 200% font a row's text column was too narrow and broke "Rs. 300.00/L" mid-number, so above 130% font the amount moves under the details, as History already does. *Default.*

## 2026-10-22 — UI polish and Home dashboard (brought forward)

- **Order.** The owner asked to polish the UI with the mockups' icons and to show today's net profit on Home before Phase 6b. The Home item of Phase 7 is done now; Phase 6b follows. *Owner.*
- **Today's figures** come from one pure function, `summarizeDay` in `domain/usecase/DaySummary.kt`, in the estimated view of CLAUDE.md section 7: completed and cancelled trips' estimates (each from its own rate snapshot) plus other income. Offers never count. Recorded expenses are shown beside the estimate, not taken out of it, matching the mockup's "after fees, fuel and maintenance reserve". Fuel logs are not used here (they belong to the cash view in Phase 7). `DaySummaryTest` includes a no-double-counting test and the Colombo midnight boundary. *Default.*
- **Labels on Home.** The mockup's "Gross income" is shown as "Earned after fees", because the figure is trip payouts after the platform fee plus cancellation fees and other income, not fares before the fee. Per km is trip profit ÷ distance driven on counted trips; other income is left out of it, since it isn't earned per km. The card is tagged "ESTIMATED", and an up or down arrow plus the sign carry the meaning as well as the colour. *Default.*
- **Home layout.** Header, net profit card, four stat cards (two per row; one per row above 130% font), the Check a Ride button with its icon, the three newest trips (any day, offers marked as in History) with "See all", then the Records rows. The mockup's bell and "Offline" pill wait for the alerts inbox (Phase 8b); no placeholder controls are shown. *Default.*
- **Record icons.** Rows in Fuel log, Expenses and Other income get a 44 dp icon tile, as in the mockups: a yellow pump for fuel, neutral tiles for expense categories (wrench, P sign, phone, toll gate, receipt) and green tiles for income types (gift, thumbs-up, star, plus). The icons are new hand-drawn 24-unit stroke vectors like the existing ones; still no icon library. Icons are decorative; each row's title names it. *Default.*
- **Fuel log layout** follows its mockup: "Spent this month" and "Actual efficiency" side by side ("Not yet" before two full tanks), a short line under them saying what the reading is based on, and rows titled "6.50 L · Rs. 414.00/L" with a green "Full tank" tag ("partial" otherwise). The suggestion became an amber notice, "Your fill-ups show 36.3 km/L", with "Keep 40" and "Update", as in the Settings mockup. Behaviour is unchanged. *Default.*
